# Parallel slices in Git worktrees

## Decide which slices can run together

When authorized to build or continue a board, choose parallel work automatically. Honor any instruction to work serially or limit the scope. Reassess after an integration, a scope change, or an agent slot opening. A ready slice has a settled contract and acceptance criteria, no blocking question, and every prerequisite (including transitive prerequisites) accepted, integrated and verified on the target branches. Check the actual dependency graph. Slice numbers and board order alone do not create dependencies. Keep intentional sequencing and ask the analyst to clarify uncertain dependencies or split a coupled slice at a stable contract before scheduling it in parallel.

Compare each proposed slice with every other slice in the batch and every active or parked worktree. Check both the files they change and the behavior they rely on:

- Map exact Owned files and tests to their repositories and normalize paths using the repository's file system rules. Two linked worktrees of the same repository share that identity. Include both parts, renames, generated files, and shared registration, routes, projects, manifests and lockfiles. Treat unknown scope or overlapping writes as a reason to serialize.
- Check whether one slice reads a contract, schema or behavior the other changes, or both touch a shared invariant, migration sequence, build configuration or generated client. A slice must be buildable and testable from the integrated base on its own. A stable, already integrated API can unblock an independent consumer.
- Isolate any writable test resources, including databases and schemas, ports, services, build output and test data. A Git worktree only isolates files in its checkout. If a required resource cannot be isolated, serialize the affected work.
- Use parallelism when it saves time after setup and combined verification. Respect available agent slots and host limits. Report the selected batch and any material reason a slice must wait. If no safe, worthwhile batch exists, run one eligible slice. Wait on conflicts with active or parked work even when scheduling a single slice. Keep running eligible work while an independent slice awaits acceptance or clarification. Release a test resource when its processes have stopped and its state has been cleaned up.

## Create and dispatch

### Choose the worktree folder

When you decide to create worktrees, ask once for the batch before creating any worktree, temporary branch or parent folder. Use the orchestrator speaker label and the **🟥 REPLY REQUIRED** format. Say which slices will run together and ask **Which absolute folder should I use for these worktrees?** Use examples that match the host, such as `C:\worktrees` or `D:\worktrees` on Windows. Wait for the developer's path. A path they already gave for the batch or explicitly chose for the rest of the board counts as the answer. When resuming an existing worktree, use its recorded path.

Check that the chosen folder is an absolute path outside existing checkouts and that the host allows writes there. Resolve symlinks and Windows junctions before checking containment. Create the parent folder if it is missing and its location is writable. If the path is invalid or unavailable, explain the blocker and ask for another folder. Offer serial work if the developer prefers it. Use the chosen folder for every new worktree in the batch, including those belonging to other repositories.

### Create the worktrees

1. Use one persistent **main worktree per repository**. It holds the local integration branch, normally `feature/<prd-name>`, or the existing feature branch recorded for that repository. The main worktree is a checkout used for integration. Never target the Git branch named `main` or another protected branch for automatic promotion. Include the board repository if separate. Verify that target branches and paths are correct and protect existing staged, changed and untracked user files. A user-kept untracked configuration file can remain in the main worktree with explicit agreement. Keep it out of commits and use the trusted configuration snapshot when dispatching.
2. In the same durable local run record used for trusted workflow inputs, record the developer's chosen parent folder and its scope, plus each slice's repository roots, integration branches, base SHAs, temporary worktree paths and branches, acceptance, integration and cleanup progress. Keep the record outside agent write scopes, at a known location available on resume. Record the plan before creating worktrees. In each affected repository, including the one that owns the slice card, create one temporary branch and worktree for that slice from the recorded integration SHA:

   ```sh
   git -C "<main-worktree>" worktree add --no-track -b "mydevfactory/<prd-name>/<slice-id>" "<slice-worktree>" "<base-sha>"
   ```

   Set `<slice-worktree>` to an unused child path inside the chosen parent, for example `D:\worktrees\SmartWebApi-smarttreestats-apps-018`. Use a distinct child name for each repository and slice. Check `git worktree list --porcelain`, the child path and the branch ref before creating it. Reuse a matching recorded worktree on resume. If setup fails partway, preserve and reconcile existing worktrees, and keep the affected slice serial or blocked until isolated work is possible. Never force-create over another checkout or branch.
3. Dispatch one fresh agent at a time per slice, concurrently across slices. Give each agent its exact worktree paths, and set its working directory when the host supports it. Require all edit and test commands to stay in the assigned worktrees and isolated test resources. Give it the slice card, PRD pointer, trusted role configuration, owned files by repository and required checks. The orchestrator owns staging, commits and integration. Capture and compare the dispatch snapshot separately in every worktree the agent can write to, including the card's worktree. Check scope before accepting the result. If an agent discovers a new overlapping file, dependency or shared resource, pause affected work and reassess before widening scope or integrating. Preserve existing edits.

## Accept, verify and integrate

Run the applicable workflow gates for the slice. A `Completed` L0/L1 slice with passing required evidence and no open change requests is eligible for automatic integration unless the developer requested sign-off. Run the per-slice Walkthrough and record an explicit ACCEPT for L2 or when the developer requested it. Keep worktrees for pending, rejected or blocked candidates. Recheck acceptance against the candidate revisions before promotion.

1. **Prepare one slice at a time.** Confirm the temporary worktrees have no active agents or uncommitted changes. In each, run `git merge --no-edit "<integration-head-sha>"` if the integration branch has advanced. Keep the main worktrees unchanged during preparation. Compare the reviewed slice delta against the new delta, each relative to its own recorded integration base. If the slice's code, tests, criteria or assumptions changed, rerun the affected workflow gates and obtain any required sign-off again. A merge conflict goes to its owning developer in the slice worktree. Abort the in-progress merge you started if needed before handing it off, preserving the committed work. A conflict or combined-check failure reopens the affected parts and counts toward the retry cap.
2. **Verify the combined revisions.** Run the affected build, test and contract checks across the prepared worktrees together, including cross-repository seams. Point commands at the prepared revisions in each repository. Record the exact previous target HEADs, prepared commit SHAs, check results and acceptance in the run record before promotion. On failure, leave the main worktrees at their previous commits and keep the candidates for repair. If a target moves or acquires a conflicting local change before promotion, prepare and verify again against the current safe target.
3. **Fast-forward the main worktrees.** Preflight all targets before changing any. Verify the recorded branch is checked out, the current HEAD matches the verified base, and tracked and staged files are clean. Verify that any explicitly retained untracked paths cannot collide with the incoming changes. Check that the base is an ancestor of the verified revision. In each target run `git -C "<main-worktree>" merge --ff-only "<verified-sha>"`. Recheck the target before each command and record the result from Git after it runs. These updates are separate across repositories. If interrupted or partially applied, retain all remaining branches and worktrees, pause further promotions, and reconcile the recorded SHA set against the actual target HEADs and ancestry. Resume the pending fast-forwards if the recorded bases and verified candidate set still match. If they changed, recheck the combined state and obtain fresh verification before proceeding. Preserve any already-promoted and unrelated commits. Do not release dependents or mark the slice integrated until all repositories contain the verified revisions.
4. **Clean up the slice.** After recording successful promotion in every repository, verify each temporary branch tip is an ancestor of its corresponding integration HEAD and that the worktree is idle, clean and belongs to this run. Preserve user files, including ignored data. Clear known disposable build outputs when necessary using the project's normal cleanup. Use `git worktree remove "<slice-worktree>"` from a different checkout, then `git branch -d "<slice-branch>"` from the integration checkout. Check both results. When cleanup fails, record cleanup as pending and retry on resume. Never force-remove, force-delete or touch unrelated worktrees. Keep the main worktrees for the next batch.
