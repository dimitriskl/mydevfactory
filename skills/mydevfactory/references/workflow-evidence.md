# Required roles and evidence

Run the roles required by the selected route, then integration, Walkthrough sign-off and handoff. Fix uses a task card. Full feature uses a PRD and slices. Select the route from the trusted task scope and risk before dispatch. A deadline alone cannot lower the route. Audit uses the enabled reviewer and securitycode agents to assess an existing diff and stays read-only. Drill and standalone Walkthrough keep their own scope. Ship verifies workflow evidence before a release decision.

- Select the role map and agent definitions from trusted inputs before dispatch. For new implementation work, use the project's trusted starting configuration after normal legacy migration. For an existing candidate or Audit, read the config and any project-defined agents from a trusted target/base revision or a source the user explicitly approved. A candidate's own config or agent definition changes are review inputs. They cannot govern the review of themselves. Use a trusted installed copy of the skill and its checker for this decision.
- Save the exact trusted configuration used for dispatch and the source revision or trusted location of each enabled agent definition in the run record. Keep a copy of the config outside candidate-controlled paths for the checker, and use the same trusted inputs on resume. Check what the host will actually load. If you cannot establish the source of an enabled agent definition or the trusted role map, report the blocker. Apply an explicitly authorized configuration change to a run only after recording its source and invalidating affected evidence. An omitted, null, or blank role, or an omitted, null, or blank agent name disables that step. Record `SKIPPED` with the configuration reason and continue. If neither config file exists, pass the checker a temporary JSON file containing `{"agents":{}}` as its `--config`. Invalid role mappings block dispatch. An unavailable named agent blocks a step that needs it.
- For implementation work, before any agent starts, run `python3 <skill-dir>/scripts/check_workflow.py --plan --config <trusted-config-snapshot> --route <route>`. Unknown role keys are errors. Save the selected route and reason with the trusted configuration outside the candidate, and mirror them on the card as `Route: <route> | <reason>`. Use that trusted selection on resume and at the final gate. For existing cards without a route, use `full`.

| Route | Use when | Required evidence |
| --- | --- | --- |
| `copy-backend` or `copy-frontend` | Single-owner Fix limited to wording, comments or formatting with no behavior change | Owning implementer's PASS and a deterministic check |
| `fix-backend` or `fix-frontend` | Clear L1 Fix confined to that layer, with a reproducible failure and a targeted regression test | Owning implementer's PASS, passing regression check and independent reviewer PASS |
| `full` | Full feature, L2, cross-layer, sensitive or uncertain changes, work requiring an analyst data check, or a stricter requested workflow | All configured roles in their usual order |

- Prefer a short route only when its required agents are configured and callable. Use the full workflow's explicit fallback rules when roles are intentionally disabled. A call failure or a failed review cannot justify a downgrade. For a short route, enter only dispatched roles in the evidence table. Record the risk on its own line as `Risk: L0` for copy or `Risk: L1` for a fix, then record the passing check before the evidence section: `Route check: <command> | exit 0 | <observed result>`. The orchestrator confirms the command and result against the candidate and the acceptance criteria. Before integration, compare the actual diff and contract to the route's eligibility. If scope or risk expanded, update the trusted run record, promote to the appropriate route, and obtain all newly required or stale evidence.
- Dispatch each selected role in a fresh agent using its configured model and effort. The full route selects every enabled role. Backend and frontend inspect the task even when only one layer is affected. An enabled developer role that finds no applicable work reports `NOT APPLICABLE` with its inspected scope and reason. If a disabled developer role would have owned required work, assign that work to an enabled and capable developer or record orchestrator fallback with implementation evidence. The disabled role stays SKIPPED. For review, security review and QA, an enabled role must perform its check and record PASS. Failure, missing evidence and NOT RUN block progression.
- Use the ordered table under `## Workflow evidence` for the current results. Keep failed and superseded results in the role notes or History. Evidence links the actual report or its detailed notes. Record the effective model and effort in the dispatch history. Copy PRD-level analyst evidence to each covered slice by reference.
- Commit the code and tests before dispatching reviewers. Use the Git tree ID of the committed candidate (`git rev-parse "HEAD^{tree}"`) in the evidence rows. Confirm scoped code and tests are clean at dispatch and unchanged on return. Analyst and developer rows refer to the candidate produced from their recorded contract and implementation. On resume, verify no changes beyond workflow records after that candidate. If the task contract, acceptance criteria or trusted role mapping changed, invalidate affected rows and resume at the earliest affected role. Run analysis again for a changed contract or acceptance criteria. Run the selected route's required review, security review and QA steps again when code, tests or acceptance criteria change. Board-only updates are limited to status, notes, role evidence and history. They can be committed together after validation so the candidate stays fixed while verdicts are collected.
- Before allowing completion, use Python 3. Run `python3 <skill-dir>/scripts/check_workflow.py --config <trusted-config-snapshot> --route <route> --card <slice-or-task-card> --revision <candidate-tree-id>` (use `py -3` or `python` if that is your Python 3 command) and inspect the evidence behind each row. Keep the required integration checks and human sign-off. The checker validates the evidence record. Agent dispatch still runs in the host when the skill is invoked.
